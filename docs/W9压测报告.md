# W9 压测报告：REST 主链路与 STOMP 实时链路

> `docs/性能验证.md` 用 `EXPLAIN ANALYZE` 回答了「索引有没有生效、扫了多少行」，
> 并明确留了一句「端到端 QPS 与延迟需要 W9 的 JMeter 场景」。
> 这份文档就是那个场景的结果。

## 1. 结论先行

| 场景 | 并发 | 时长 | 采样数 | 吞吐 | 平均延迟 | 错误率 |
|---|---|---|---|---|---|---|
| REST 主链路 | 30 线程 | 60 s | 14 803 | **245.7 req/s** | 111.6 ms | **0.00 %** |
| STOMP 实时链路 | 10 线程 | 30 s | 7 188 | 238.8 op/s | 38.5 ms | **0.00 %** |

拆到接口：

| 接口 / 操作 | 采样数 | 平均 | 最大 |
|---|---|---|---|
| `POST /api/auth/login` | 30 | 172.4 ms | 287 ms |
| `GET /api/sessions` | 4 930 | 67.9 ms | 335 ms |
| `GET /api/sessions/{id}/messages` | 4 924 | 33.6 ms | 184 ms |
| `POST /api/sessions/{id}/read` | 4 919 | **233.2 ms** | 583 ms |
| WebSocket 握手 | 10 | 6.2 ms | 10 ms |
| STOMP `CONNECT` → 读到 `CONNECTED` | 10 | 8.3 ms | 14 ms |
| 发送消息（帧写出） | 3 569 | 0.2 ms | 35 ms |
| **发送 → 收到 ack（端到端）** | 3 569 | **76.9 ms** | 173 ms |

发消息的有效吞吐是 **3 569 条 / 30 s ≈ 119 条/秒**，端到端 ack 平均 77 ms。

三条值得记下来的结论：

1. **零错误**。两个场景在持续加压下都没有出现 5xx、超时或断言失败，
   说明限流、幂等、行锁这几条路径在 30 并发 × 60 秒下是稳的。
2. **最慢的不是发消息，是报已读**（233 ms，是拉消息的 7 倍）。原因已定位，见第 4 节。
3. **发消息的瓶颈不在 WebSocket 帧写出**（0.2 ms），而在服务端那条链路上：
   落库 + 群广播 + 已读游标。客户端侧几乎没有开销。

## 2. 环境与口径

| 项 | 值 |
|---|---|
| JMeter | 5.6.3（`docs/jmeter/`，需 `websocket-samplers` 插件） |
| JDK | 21 |
| 后端 | 单实例 Spring Boot 8083，未做 JVM 调参 |
| MySQL / Redis | 本机 Docker（3307 / 6380），未做参数调优 |
| 数据量 | `im_message` 约 4 千行（压测前），并发会话 11 个 |
| 客户端 | 与服务端同机，走 localhost，因此延迟里没有网络 RTT |

**这是一台机器上的单实例基线，不是容量上限。** 同机意味着 JMeter 与被压服务抢同一份
CPU，真实部署下这个数字会更高；反过来，真实网络 RTT 会把这 111 ms 的均值抬上去。
它的用途是「做一次可比对的基线」和「找出最慢的那一段」，不是对外承诺 SLA。

### 为什么登录只压一次

两个计划都把登录放进 `Once Only Controller`。不这么做，30 线程会变成「登录接口压测」，
测出来的是 BCrypt 的计算开销，而不是聊天的开销。登录单独看：30 次并发登录平均 172 ms，
其中绝大部分是 BCrypt 校验——有意为之，密码哈希本就该慢。

### 为什么 STOMP 单独一个计划

聊天消息完全不经过 REST。REST 压测再漂亮也证明不了「发消息」这条路——
它压的是 Tomcat 线程池 + MySQL，而发消息压的是 WebSocket 容器 + 群广播 + 一次落库。
两个计划分别对应这两段代码。

## 3. 复现

```bash
# 前置：后端与依赖已启动（见 本地运行说明.md）
# 前置：JMeter 装好 websocket-samplers 插件

# REST 主链路：30 线程 × 60 秒
jmeter -n -t docs/jmeter/w9-rest-load.jmx \
       -l docs/jmeter/rest.jtl \
       -e -o docs/jmeter/report/rest-report

# STOMP 实时链路：10 线程 × 30 秒
jmeter -n -t docs/jmeter/w9-ws-stomp.jmx \
       -l docs/jmeter/ws.jtl \
       -e -o docs/jmeter/report/ws-report
```

线程数与时长是计划里的**变量**（`THREADS` / `DURATION`），改命令行即可，不必改 XML：

```bash
jmeter -n -t docs/jmeter/w9-rest-load.jmx -JTHREADS=100 -JDURATION=120 \
       -l docs/jmeter/rest.jtl -e -o docs/jmeter/report/rest-report
```

HTML 报告在 `docs/jmeter/report/`（`.gitignore` 已排除，属生成物）。

## 4. 发现的问题：报已读的 233 ms

`POST /api/sessions/{id}/read` 平均 233 ms，最大 583 ms，是同一轮压测里最慢的接口。

`ReadService.markRead` 一共四条语句，单次都在毫秒级：

```java
sessionService.assertMember(sessionId, userId);   // 1 次成员校验查询
cursorMapper.upsert(sessionId, userId, lastReadSeq);  // 游标行 upsert
inboxMapper.deleteUpTo(userId, sessionId, lastReadSeq);
inboxMapper.countUnread(userId, sessionId);
```

慢的不是语句，是**锁**。压测里 30 个线程用的都是同一个账号，于是 30 个线程
抢的是 `im_read_cursor` 上**同一行**（主键 `session_id + user_id`）。
`UPDATE` 在该行上取排他锁，后面的事务排队，平均耗时自然被排队时长撑起来了。

这不是缺陷，是行锁在正常工作——同一个人的已读游标本来就必须串行推进。
它给 W9 的启示有两条：

1. **压测口径要说清楚。** 如果 30 个线程用 30 个不同账号，这个接口会回到个位数毫秒；
   用同一账号压出来的 233 ms 反映的是「单用户高频上报」这一种不太真实的模式。
   报告里保留这个数字而不是掩盖它，因为它正好量化了「同一用户并发上报会排队」。
2. **客户端不该高频上报。** 前端 `markRead` 已经做了「读到最新且无未读就不再请求」的短路，
   切会话才报一次。如果把已读做成定时任务（比如每秒一次），这个行锁就会变成热点的热点。

这一条 W9 不修，因为修它需要改数据模型（比如把游标改成 append-only 再取 MAX），
代价远大于收益，而当前实现有短路保护、真实使用下不会形成热点。

## 5. 压测数据没有留在演示库里

两个场景一共往演示群写了 3 569 条 `perf <uuid>` 消息。压测结束后已清理：

```sql
delete from im_inbox   where session_id = 109903710661906432 and seq > 8;
delete from im_message where session_id = 109903710661906432 and seq > 8;
-- 会话摘要按剩余的最大 seq 重算
```

清理后该群恢复到压测前的 8 条消息，会话列表的摘要与未读数也已按真实数据重算。
**压测应当造独立库**（`docs/性能验证.md` 用的就是 `im_perf`），这次图省事直接压了演示库，
属于走捷径，记在这里避免下次再犯。
