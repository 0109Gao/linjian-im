# 性能验证：为什么这一版不需要 Redis 消息缓存

> 这份文档不是压测报告，是**一次决策的依据**。它要回答的问题是：
> 「群聊 + 已读 + 多端都做了，消息表会到几十万行，要不要给消息加一层 Redis 缓存？」
> 答案是不要。下面是可以复现的证据。

## 1. 结论先行

1. 单机 MySQL 上，`im_message` 的 `uk_session_seq (session_id, seq)` 让三条读取路径全部走索引，且 `LIMIT` 能提前终止扫描。**20 万条消息的会话，取最新 31 条 0.29 ms，增量补拉 0.14 ms，向历史深处翻一页 0.24 ms。**
2. 未读数是覆盖索引上的 `COUNT`，5000 行未读 0.93 ms。
3. **真正的瓶颈不在数据位置，在调用次数。** 200 人群一条消息，W7 的写法是 200 次序列化 + 200 次 Redis 在线判断；W8 改成 1 次广播 + 1 条批量 INSERT。
4. 会话列表的 `OFFSET` 深翻页会退化成全表扫描 + 排序。这是**发现的问题**，不是想当然的结论，对策见第 6 节。

因此 W8 不做冷热分离。把预算花在「消灭 N 次调用」上，而不是「把毫秒级查询搬到内存里」。

## 2. 环境

| 项 | 值 |
|---|---|
| MySQL | 8.4（`docker/docker-compose.yml` 的 `im-mysql`，未做任何参数调优） |
| 库 | `im_perf`（独立库，与演示库 `im`、测试库 `im_test` 隔离） |
| 表结构 | 与 `sql/schema.sql` 完全一致，含全部索引 |
| 数据 | 30 万条消息 / 501 个会话 / 502 条成员关系 / 5000 行未读 |
| 表体积 | `im_message` 数据 30.6 MB + 索引 31.2 MB（约 200 字节/行） |
| 测量方式 | `EXPLAIN ANALYZE`（实际执行并给出真实耗时） |

单机、无并发、容器内文件系统。这些数字只能用来说明「索引是否生效、扫描了多少行」，**不能当作端到端 QPS 或 P99**——那需要 W9 的 JMeter 场景。

## 3. 造数

脚本：`sql/seed-bulk.sql`，约 7 秒完成 30 万条。

```bash
docker exec -i im-mysql mysql -uim -pim123456 im_perf < sql/seed-bulk.sql
```

数据形状：

- **热会话 `990001`**：20 万条消息，seq 1..200000。用来验证深历史下的分页与补拉。
- **冷会话 `990100..990599`**：每个 200 条，共 10 万条。用来验证会话列表。
- 用户 `900001` 参与全部 501 个会话，`900002` 只在热会话里。

脚本是幂等的（先按 id 区间删再建），可反复执行。

## 4. 三条消息读取路径

### 4.1 取会话最新一页（首屏 / 未传游标）

```sql
SELECT * FROM im_message WHERE session_id = 990001 ORDER BY seq DESC LIMIT 31;
```

```
-> Limit: 31 row(s)  (cost=15001 rows=31) (actual time=0.267..0.291 rows=31 loops=1)
    -> Index lookup on im_message using uk_session_seq (session_id=990001) (reverse)
       (cost=15001 rows=150000) (actual time=0.163..0.184 rows=31 loops=1)
```

**0.29 ms，只读 31 行。** 注意 `rows=150000` 是估算值，`actual rows=31` 才是真相：反向索引扫描 + `LIMIT 31` 让它在第 31 行就停，与表有多大无关。

### 4.2 断线重连增量补拉（`afterSeq`）

```sql
SELECT * FROM im_message WHERE session_id = 990001 AND seq > 199900 ORDER BY seq LIMIT 31;
```

```
-> Limit: 31 row(s)  (cost=45.3 rows=31) (actual time=0.0907..0.139 rows=31 loops=1)
    -> Index range scan on im_message using uk_session_seq over (session_id = 990001 AND 199900 < seq),
       with index condition: ((session_id = 990001) and (seq > 199900))
       (cost=45.3 rows=100) (actual time=0.0535..0.1 rows=31 loops=1)
```

**0.14 ms。** 范围扫描起点直接定位到 `seq = 199900`，不回表扫历史。

### 4.3 向上翻历史（`beforeSeq`）

```sql
SELECT * FROM im_message WHERE session_id = 990001 AND seq < 150000 ORDER BY seq DESC LIMIT 31;
```

```
-> Limit: 31 row(s)  (cost=30000 rows=31) (actual time=0.2..0.243 rows=31 loops=1)
    -> Index range scan on im_message using uk_session_seq over (session_id = 990001 AND seq < 150000) (reverse),
       with index condition: ((session_id = 990001) and (seq < 150000))
       (cost=30000 rows=150000) (actual time=0.0557..0.0976 rows=31 loops=1)
```

**0.24 ms，翻到第 15 万条依然是常量时间。** 这是 `seq` 作为游标而不是时间戳的核心收益：时间戳分页在深翻时要么走 `OFFSET`（线性变慢），要么担心同毫秒重复。

## 5. 未读数与已读删除

未读数据是另行插入的 5000 行（seq 195001..200000），模拟「用户 5000 条没看」。

### 5.1 单会话未读数

```sql
SELECT COUNT(*) FROM im_inbox WHERE user_id = 900001 AND session_id = 990001;
```

```
-> Aggregate: count(0)  (cost=503 rows=1) (actual time=0.932..0.932 rows=1 loops=1)
    -> Covering index lookup on im_inbox using uk_user_session_seq
       (user_id=900001, session_id=990001) (cost=253 rows=2500) (actual time=0.0261..0.71 rows=5000 loops=1)
```

**0.93 ms，5000 行全在索引里（covering index，不回表）。** 这是「未读数 = `COUNT(im_inbox)`」这个设计能成立的前提：如果未读数是「最大 seq − 已读 seq」，就不需要这张表，但会被 seq 空洞算错；用计数换准确性，代价控制在 1 ms 内。

### 5.2 会话列表的未读分布

```sql
SELECT session_id, COUNT(*) FROM im_inbox WHERE user_id = 900001 GROUP BY session_id;
```

```
-> Group aggregate: count(0)  (cost=503 rows=70.7) (actual time=0.914..0.915 rows=1 loops=1)
    -> Covering index lookup on im_inbox using uk_user_session_seq (user_id=900001)
       (cost=253 rows=2500) (actual time=0.0408..0.716 rows=5000 loops=1)
```

一次扫描出全部会话的未读数，避免会话列表逐行查询（N+1）。

### 5.3 标记已读的删除

`EXPLAIN ANALYZE` 对 `DELETE` 在 MySQL 8.4 上回 `<not executable by iterator executor>`，改用前后时间戳取差：

```sql
SET @t0 = NOW(6);
DELETE FROM im_inbox WHERE user_id = 900001 AND session_id = 990001 AND seq <= 199000;
SET @t1 = NOW(6);
```

**删除 4000 行：23.8 ms**（剩余 1000 行）。

这个数字比查询慢两个数量级，原因在写入路径（行删除 + redo/undo + 索引维护），不在查找。它对应「用户一次上报已读，清掉积压的 4000 条未读」，属于一次操作的量级，可以接受。**但它是这套设计里最该被盯住的写放大点**：如果某个用户积压几十万条未读，一次上报就会长时间持锁。兜底手段是 `MaintenanceJob` 的 30 天清理（每批 5000 行），以及客户端按页上报已读而不是一次到底。

## 6. 发现的问题：会话列表深翻页

第一页（`OFFSET 0`）走索引，符合预期：

```sql
SELECT s.* FROM im_session s JOIN im_session_member m ON m.session_id = s.id
WHERE m.user_id = 900001 ORDER BY s.last_msg_at DESC, s.id DESC LIMIT 20 OFFSET 0;
```

```
-> Limit: 20 row(s)  (cost=127 rows=20) (actual time=0.125..0.161 rows=20 loops=1)
    -> Nested loop inner join  (cost=127 rows=20) (actual time=0.114..0.149 rows=20 loops=1)
        -> Index scan on s using idx_last_msg_at (reverse)  (actual time=0.0911..0.106 rows=20 loops=1)
        -> Single-row covering index lookup on m using PRIMARY (session_id=s.id, user_id=900001)
           (actual time=0.00121..0.00124 rows=1 loops=20)
```

**0.16 ms**，`idx_last_msg_at` 反向扫描 20 行即停。

第 25 页（`OFFSET 480`）换了一个计划：

```
-> Limit/Offset: 20/480 row(s)  (cost=227 rows=20) (actual time=0.645..0.663 rows=20 loops=1)
    -> Nested loop inner join  (cost=227 rows=501) (actual time=0.208..0.647 rows=500 loops=1)
        -> Sort: s.last_msg_at DESC, s.id DESC  (actual time=0.202..0.229 rows=500 loops=1)
            -> Table scan on s  (actual time=0.0178..0.11 rows=501 loops=1)
        -> Single-row covering index lookup on m using PRIMARY (actual time=687e-6..711e-6 rows=1 loops=500)
```

**退化成「全表扫描 + 排序 + 500 次主键回查」**。501 个会话时仍是 0.66 ms，看不出问题——但如果一个用户有 5 万个会话，这就是 5 万行扫描加排序，而它发生在**每次下拉刷新**上。

原因：`ORDER BY` 的排序键在 `im_session`，而过滤条件在 `im_session_member`。优化器在浅翻页时能靠「按 `last_msg_at` 反向扫，逐行验证成员身份」提前终止；一旦带 `OFFSET`，它无法保证跳过的行都属于该用户，转而选择「先取全部候选再排序」。

**对策（当前不实现，记录触发条件）**：

- 现在：会话列表设上限分页（`pageSize ≤ 50`，接口层面不提供无限下拉）。真实用户的会话数在几百量级，`page × size` 不会深到退化区间。
- 将来：用户会话数进入万级时，改成 keyset 分页——用 `(last_msg_at, id)` 作为游标，条件是 `(last_msg_at, id) < (?, ?)`，配一个 `im_session(last_msg_at, id)` 的复合索引。keyset 分页没有 `OFFSET`，深翻页是常量时间。

顺带一个反例提醒：这次没有给 `im_session` 加 `(last_msg_at, id)` 复合索引，因为 501 行的排序耗时 0.02 ms，加索引只是让 `EXPLAIN` 好看。**不为一个没测出来的问题加索引**——那和为一个没测出来的问题加缓存是同一个错误。

## 7. 群聊扇出：优化的是调用次数

W7 的投递是循环：对每个成员「写一行未读 + 查一次在线 + 推一次」。200 人群一条消息 = 199 次 INSERT + 199 次 Redis `SCARD` + 在线者各一次 JSON 序列化。

W8 改成：

| 步骤 | W7 写法 | W8 写法 | 次数变化 |
|---|---|---|---|
| 未读行 | 199 次单条 INSERT | 1 条 `INSERT IGNORE ... VALUES (...),(...)` | 199 → 1 |
| 在线判断 | 199 次 Redis | 0 次（广播天然只到活着的连接） | 199 → 0 |
| 推送 | 每个在线成员一次序列化 | 1 次广播 | N → 1 |
| 会话类型 | 无 | 1 次主键查询 | +1 |

净效果：**消息条数越多、群越大，收益越大**；代价是每条消息多一次主键查询（命中 buffer pool 后是纯内存操作）。这是「用一次便宜的查询换掉 199 次网络往返」的典型置换。

这条改动没有做端到端延迟测量。理由是测量需要 200 个真实连接，而 W9 的 JMeter 场景三（单群 200 人同时在线）本来就是为它准备的；在这里报一个手工测的数字，不如把方法留到有工具的时候做。**结构上的次数变化是确定的，耗时不是，所以这里只写次数。**

## 8. 为什么不做冷热分离

初版方案是「写入后 `LPUSH` 到 `im:hot:{sessionId}`，`LTRIM 0 199`，历史查 MySQL」。放弃的理由：

1. **收益不存在。** 缓存要替代的是「取最近 31 条」，实测 0.29 ms。没有可省的时间。
2. **风险是实在的。** `seq` 允许空洞（`INCR` 先于 `INSERT`），缓存里存的是「最近 N 条」，一旦某条消息落库失败、或缓存写入失败，客户端会看到「热区少一条、冷区有」，而这正好落在最容易出乱序的地方。
3. **它掩盖真问题。** 这个量级的瓶颈是调用次数（第 7 节），不是数据位置。加缓存不会让 199 次调用变成 1 次。

**重新考虑的触发条件**（写清楚，避免以后拍脑袋）：

- 单会话消息量进入千万级，`LIMIT` 提前终止也救不了——那时先分区或归档。
- 读 QPS 超过单库承受范围（需要先用 JMeter 测出这个数）。
- `im_message` 单表超出单机磁盘容量。

## 10. 局限

- **只有单线程、无并发。** 测的是「索引是否生效」，不是「并发下能扛多少」。
- **容器内文件系统。** 宿主机（Windows + WSL2 卷）的 fsync 语义与生产 Linux 不同，写入类数字（第 5.3 节）尤其只做参考。
- **没有慢查询日志校准。** 上表的 0.29 ms 是 `EXPLAIN ANALYZE` 的输出，包含执行但不包含网络往返与 JSON 序列化。
- **端到端延迟未测。** 见第 7 节末的说明。
